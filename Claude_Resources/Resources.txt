- BGG Link (the game's BGG page; bgg.com for games not found on BGG),
- Difficulty (BGG's average weight, stored and displayed exactly as BGG gives it, with a dot: 2.0488; comes only from BGG and can't be entered by users, so games not found on BGG show "–").
  Shown with a slim bar the full height of its cell, filling from the bottom (0–5 → empty–full), on a heat scale from
  green (easiest) to red (hardest) – decided 2026-11-23, replaces the coloured cell; on the board and in Baza gier,
- Game picture (set by BGG API and stored in database; random colored square with game name text on top when there is none.
Users can upload a cover only for a game not found on BGG: the box shows the 🗁 button on a light-gray background, covering 1/4 of it. Users can't replace an existing cover;
BGG images must never be hot-linked: download once, resize as needed and serve a copy from our server, per a BGG admin's forum post.
That post also says image licences are set by the original uploader, and using an image without a suitable licence needs the uploader's permission),
- Game slots (interactable by users; users can click on a slot to take it, or click again to free it; table owner can also click on a slot to free it,
including other users' slots;
number of slots equals number of players: taken from BGG API from max players count; for early development randomize 1-6),

Game lookup (adding a table):
- No "new table" form: the last row of the list is, for logged-in users, a free-text game name field with a "Utwórz stół" button that creates the table.
- When that field loses focus the game is looked up, and the rest of the row's columns appear (slots taken, table type, hour, players, BGG link, difficulty, cover). Enter doesn't create the table.
- Users can type any title of a game. The catalog is checked first, by primary and alternate names, and only then BGG (also by all names).
- A single exact match is picked automatically; otherwise the user picks from a list (BGG lists separate editions, e.g. Citadels 2000 and 2016), or rejects it and adds the game by hand.
- The picked game is saved to the catalog with its alternate names and cover (BGG thumbnail), so BGG is only contacted once per game. The BGG button searches BGG again, e.g. for another edition.
- A table shows the title the user typed, even when it's an alternate name. In the catalog, editions sharing a name get the year added, because catalog names are unique.
- BGG takes priority over hand-added games: they're used only when BGG finds nothing or can't be reached, or the user rejects its results. A hand-added game matching an imported BGG game becomes that game, including its cover.
- BGG is contacted only from the server, at most once per 5 seconds. The "Powered by BGG" logo linking to BGG is shown in the bottom-right corner of the menu drawer, as BGG's terms require.
- Every table created with "Utwórz stół" (on the board or on Baza gier) records the game name used in the database (TablePhrases: phrase, game, user, time). Phrases outlive tables and the weekly reset; the user is stored but never shown. Renaming a table doesn't record one.
- No "recently used names" list under the game-name field (the "Ostatnio:" chips were removed); the phrases are only recorded.

Table owner:
- Owner can rename the table (🏷️): the game name is typed again and looked up like a new table (catalog, then BGG). Renaming wipes all slots: every player leaves; a seated owner keeps the first slot. The popup warns about this before saving.
  Decided 2026-11-23: the rename popup also has the new-table row's details – Zajęte, Stół (kind), Godzina, Graczy,
  BGG link, Trudność and the cover (🗁 upload only for a game without BGG data and without a cover) – labelled, two per
  line. They start at the table's current values (Zajęte at 0, since renaming frees the seats); a newly looked-up game
  brings its defaults (kind, player count) as for a new table; the hour stays unless changed (user: "Keep it"). The
  chosen values are saved (before: a BGG game's player count replaced the table's, kind and hour stayed). The hour
  picker opens on top of the rename popup, which stays open; Escape closes the innermost popup first. Same rules as a
  new table, checked on the server (tryChangeGame). Desktop first (branch feature/rename-with-details); the phone
  sheet adapts it on the phone branch.
- Owner always sits in the first slot and can free it; while it is vacant they keep owner rights and can only return to the first slot.
- The player who takes the vacated first slot becomes the new owner; the previous owner becomes a regular player.
- The first slot can't be marked as taken by owner.
- Owner can remove the table entirely (two clicks: ❌ turns the whole button solid green with a large white ✓, a second click deletes; it reverts on Escape, a click anywhere else, or after 4 seconds); the game stays in the catalog.
- Popups triggered by the action buttons (renaming, and any future action behind the placeholders) open next to the button that called them.
- Owner can add other players by right-clicking a free or "taken by owner" slot (not the first slot, which stays the owner's). A popup lists registered users, with a free-text name field at the bottom.
- Adding a player to a slot marked as taken lowers the slots taken counter by one; the player lands on the chosen slot.

Admin:
- Admin can do everything the owner can on any table: change settings, add and remove players (including removing the owner by left-clicking their slot), remove the table.
- Admin can right-click the first slot to assign a new owner, choosing from registered users. Whoever sat there leaves the table; a new owner already seated elsewhere moves to the first slot.

- A button in the bottom left corner, visible only to admins, expands a note reminding them of their capabilities. Keep the note up to date when admin capabilities change.
- Admin toolbox: a "🧰 Narzędzia admina" button right of the note's button; the toolbox expands upwards above it.
  Toolbox: dark-gray background with a white border; list items are dark-gray buttons with white text;
  switches are light-gray, distinguishable from the background (the knob's side shows ON/OFF).
  Items:
  - "Wyczyść listę stołów": removes every table, in two clicks: the first turns the button green and says how many tables will go ("✓ Kliknij ponownie – usunie N stołów"), the second clears the list; it reverts like the delete buttons. Games stay in the catalog.
  - "Auto" switch next to it (tooltip explains it): when ON, the list of tables is cleared every Monday at midnight,
    server time. A Monday missed while the app was down is caught up once on startup. Turning it on midweek
    doesn't clear the board until the next Monday.
  - "💾 Miejsce na dysku" (added 2026-11-08): one click shows, under the button, the server disk's used/total
    space with a bar (green, yellow from 75%, red from 90%), free space, and the sizes of the database file
    (incl. -wal/-shm; covers live in it) and of the feedback folder. Clicking again refreshes it. Read-only.

Roles (decided 2026-11-08):
- Roles: Owner (main admin), Admin, User. The Owner always also has Admin, so everything an admin can do, the Owner can.
- The Owner is the account configured as Admin:UserName; the seeder gives it Owner + Admin. It can't be assigned,
  changed or deleted on the users page (shown as an "Owner" badge).
- Admins can make users admins and delete regular users. Only the Owner can take the Admin role away from
  someone or delete an admin's account. Enforced on the server (re-checked against the database on each action);
  the controls are also disabled for other admins.
- Normal user mode hides Owner as well as Admin.

- Logged so far: a user taking a seat at a table themselves (JoinedTable, saved in the same transaction as the seat),

Accounts / user names (decided 2026-11-08):
- Registration asks for a user name ("Nazwa użytkownika") separate from the e-mail. It is shown to other players.
  Rules: 3–20 characters, letters (incl. Polish), digits, spaces, ".", "_", "-"; no "@". Must be unique.
  Spaces at the edges are trimmed and runs of spaces collapse to one before checking ("  Jan   Nowak " → "Jan Nowak").
- E-mail addresses must be unique. Login accepts either the e-mail or the user name.
- E-mail format is checked wherever an address is saved (registration, admin "Dodaj użytkownika", e-mail change
  in the profile): name@domain.tld, ASCII letters/digits and . _ % + - before '@', no leading/trailing/double dots,
  top-level domain of at least 2 letters, max 254 chars. Surrounding spaces are trimmed.
  Error: "Podaj poprawny adres e-mail, np. jan.nowak@example.com."
- The admin "Dodaj użytkownika" form also asks for a user name, with the same rules as registration.
- Changing the e-mail in the profile doesn't change the user name. Older accounts whose user name is their
  e-mail keep both in sync (and keep showing the part before '@').
- NEW (requested 2026-11-11): every user can change their own user name on "Profil" (/Account/Manage; the field
  was read-only before), admins and the Owner included. Same rules as registration and unique. Saved together with
  the phone number ("Zapisz"); with any field error nothing is saved. Their seats show the new name, open boards
  refresh, and it's logged in Dziennik as UserRenamed (actor = the user, under the new name). The page saves in
  place (no reload). The Owner and the development test users are found by e-mail at startup too, so a renamed
  account isn't created again.

- BGG (decided 2026-11-22): every game of the sheet is looked up on BGG and added to the catalog (BGG details + cover)
  when it isn't there yet. The sheet's BGG link says which game it is; the JSON feed only has the cell text "Link", so
  the links are read from the tab's public HTML view (SHEET_IMPORT_LINKS_URL, …/htmlview/sheet?headers=true&gid=0).
  Without a link the title is searched on BGG and used only when there is one clear match (one exact title, or the only
  result) – the same rule as the new-table row; a title is searched once per server run. Without BGG_TOKEN, when BGG is
  down or nothing clear is found, the old name matching applies. Tables keep the sheet's seat count; the catalog game
  keeps BGG's. BGG is asked before the sync, outside its transaction (5 s between requests must not block the database).
- 1:1: imported tables (PlayTable.ImportKey = normalized title + "#occurrence") and imported seats (TableSlot.IsImported)
  are added, updated and removed to match the sheet. Renaming a row in the sheet replaces its table.
- App data stays: tables created in the app are never touched; seats taken in the app at an imported table are kept,
  moved to the lowest free seat if the sheet gives theirs to someone else, and dropped (logged) only when no seat is left.
  A table removed from the sheet goes with all its seats.
- Games: the title's BGG game (see above), else a catalog game with the same name / alternate name, is reused unchanged
  (only a missing weight is filled in, and only on a game without BGG data);
  otherwise a game is created with Game.IsFromSheet, deleted again once no table uses it. Attaching BGG data clears the flag.
- Imported tables list in the sheet's row order (PlayTable.ImportOrder, set at every import).
  The "imported from Excel" divider line sits directly after the website's own tables, with about five empty text
  lines (~106px) above it; all imported tables are below it (design 20261109-162610, decided 2026-11-09).
  The new-table row (and its draft panel) belongs to the website's part: it sits after the website's own tables,
  above the divider, not at the very bottom below the imported ones (decided 2026-11-12). The blank space between
  the new-table row and the divider is 30% smaller than the original five lines: ~74px (4.55rem, decided 2026-11-12).
- Known difference: the app places "Zajęte" marks on the highest-numbered free seats, the sheet usually on the first ones;
  the count matches, the positions may not. Admin edits to an imported table are overwritten at the next import.

Phase 2 – accounts (decided 2026-11-10):
- Same pages, wording and rules as the .NET account pages, except these deliberate differences:
  - Lockout is ON: 5 wrong passwords in a row lock the account for 5 minutes (Identity's defaults). The .NET login
    passed lockoutOnFailure: false, so its lockout page was never reached.
  - Login with the right password but an unconfirmed e-mail says so ("Błąd: najpierw potwierdź adres e-mail – link
    jest w wiadomości od nas."); .NET showed the generic "nieprawidłowy login lub hasło". Only someone who knows the
    password sees it.
  - After registering, the confirmation page URL carries the user id instead of the e-mail address
    (/Account/RegisterConfirmation?userId=…), so addresses don't end up in server logs.
  - The Owner can't delete their own account on the personal-data page ("nobody can delete the Owner").
  - Profile menu: Profil, E-mail, Hasło, Dane osobowe (2FA, passkeys and external logins left out of v1). The
    registration page has no "Zarejestruj się przez inną usługę" column.
  - The personal-data download has the same keys as .NET, without the 2FA/authenticator entries.
  - Without EMAIL_HOST, Development also writes each unsent e-mail (with its link) to the log, so password reset and
    e-mail change can be tried locally. Never in production.
  - URLs are case-insensitive, as in ASP.NET Core (/account/login works).
- Sessions: stored in the database (sessions table, SHA-256 of the cookie's random id), 14 days, sliding;
  "Zapamiętaj mnie" = persistent cookie. Logout deletes the session; a password change logs out the user's other
  sessions, a password reset logs out all of them. Role changes apply on the next request.
- Cookies: HttpOnly, SameSite=Lax; in production also Secure with the __Host- prefix (__Host-session, __Host-csrf).
- CSRF: every POST needs the hidden _csrf field (signed token equal to the csrf cookie) and must not come from
  another site (Sec-Fetch-Site / Origin). Failure = 403 "Błąd: formularz wygasł albo został wysłany z innej strony…".
- Passwords: old ASP.NET Identity v3 hashes verify and are replaced by scrypt (N=2^14, r=8, p=5) on the next login.
  Password rules as Identity: production needs 6+ characters with a digit, lower- and upper-case letter and a
  special character; development only the length. Forms: 6–100 characters.
- E-mail links (confirm, change e-mail, reset password) use one-time random tokens valid 24 h, stored hashed.
- Roles are one column: owner / admin / user. The Owner comes from ADMIN_USER_NAME / ADMIN_EMAIL / ADMIN_PASSWORD.
- New settings: PUBLIC_URL (links in e-mails), APP_SECRET (required in production), ADMIN_*, EMAIL_* (see
  node-app/.env.example). Packages added: @fastify/cookie, @fastify/formbody, nodemailer, dev @types/nodemailer.
- Deleting an account (decided 2026-11-10): the user's seats and the tables they own STAY on the board. Only the
  link to the deleted account is cleared (user id set to null in the database), so the seat keeps showing the
  player's name and an owned table becomes a table without an owner (PlayTable already handles those).
  Built in phase 3 with the board tables.
- Admin "normal user mode" (decided 2026-11-10): stays, ported unchanged (admins switch it on to see the app as a
  regular user; the Admin/Owner roles are ignored app-wide until switched off). Built in phase 4 with the admin pages.

Phase 3 – board (decided 2026-11-10):
- Same board, rules and wording as Tables.razor (admin dock/toolbox, normal user mode and the sheet import come in phase 4).
- NEW: live updates. After every change the server sends all open pages a small notice (table id + version, no user
  data); each page re-fetches the changed row(s) with its own rights. Catch-up after a disconnect or server restart
  by version/boot id; reconnect with growing delays up to 30 s; a small "Łączenie…" notice after 3 s offline.
  WebSocket connections from other sites are refused (Origin check).
- Actions are fetch() POSTs (JSON, or multipart for a new table with a cover) with the CSRF token in a header;
  answers are JSON { ok, message | error } shown as the same dismissible alerts as in .NET.

- Uploaded covers are checked by content (magic bytes), max 2 MB enforced while receiving.
- The seat count in the new-table row is prefilled (BGG's / the catalog's count, else drawn at random 1–6) and can be
  changed by the user; the server accepts a whole number from 1 to the limit. The catalog game's count is never
  changed by table creation (a hand-added game is stored with the count of the table that created it). (2026-11-22) New BGG_TOKEN setting (without it, lookups use the catalog and hand-added games only).
- Deleted accounts: their seats keep the name, their tables lose the owner (owner/user ids set to null).
- Packages added: fast-xml-parser, @fastify/websocket, @fastify/multipart; dev @types/ws, @playwright/test
