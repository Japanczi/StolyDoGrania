Differences from the main spec (decided 2026-11-10):
- NEW: board changes appear live for every open page (WebSocket), not only after a reload.
  The server only announces "table N changed" (plus a version number); each page fetches the updated row over HTTP
  with its own login, so pushes never carry user-specific or admin-only data. After a reconnect the page catches up
  by comparing the version (whole board refetched if anything was missed). Own actions update the row without a
  full reload; without JS, forms still work as normal posts.
- OUT of v1: passkeys, two-factor authentication, external logins (and their pages). 2FA comes later: the login
  is a step-by-step flow and sessions carry an auth level, so a second step can be inserted.
- Accounts and passwords are kept: old ASP.NET Identity v3 hashes are verified, and re-hashed (scrypt) on the next
  successful login. Users are logged out once at cutover (new cookies).
- Existing 2FA/passkey settings and external logins are not migrated; the migration script lists any account that
  had 2FA switched on.
- Roles are stored as one value per user (owner / admin / user) instead of Identity's role tables; the rules are
  unchanged (Owner is always also Admin, only the Owner manages admins, nobody changes the Owner).
- Ported too (unchanged rules from the main spec): dev-only tools (page designer with the same JSON format, 4 test
  users), the temporary Google sheet import (kept isolated in src/import/), the feedback box file format.

Stack (decided 2026-11-10, phase 0 approved with all recommendations):
- Node.js current LTS; TypeScript run directly by Node (type stripping), tsc only type-checks.
- Fastify; HTML from our own escaping `html` tagged templates; Bootstrap 5; plain browser JS with // @ts-check.
- SQLite (stay on Mikrus 2.1): better-sqlite3 + Kysely; hand-written, numbered migrations.
- Hand-written database sessions (only the id's hash stored; HttpOnly, SameSite=Lax, Secure cookies);
  CSRF token + same-origin check on every non-GET request; Origin check on the WebSocket upgrade.
- WebSocket via @fastify/websocket with a hand-written reconnect (growing delays, max 30 s).
- Tests: node:test + Fastify inject() + in-memory SQLite; a few Playwright browser tests from phase 3.
- Background jobs (weekly reset, sheet import): in-process timers; Europe/Warsaw time computed explicitly.
- Config: .env locally (git-ignored, .env.example committed), environment variables on the server; validated at startup.
- npm packages approved for adding when their phase needs them: fastify, @fastify/cookie, @fastify/formbody,
  @fastify/static, @fastify/multipart, @fastify/websocket, kysely, better-sqlite3, nodemailer, fast-xml-parser;
  dev: typescript, @types/node, @types/better-sqlite3, @playwright/test. Others: ask first.

Phase 1 details (decided 2026-11-10):
- Node 26 LTS (installed on the PC with winget), npm 11, TypeScript 7. Installed so far: fastify, @fastify/static,
  kysely, better-sqlite3 (13: bundles Windows + Linux binaries, so nothing is compiled and the same packages work on
  Mikrus; its compile-from-source install script is denied via "allowScripts").
- Local dev runs on port 5180 (the .NET app uses 5223), so both can run side by side. Run from node-app/:
  npm run dev. Local database: node-app/data/planszowkarz.db (git-ignored).
- Migrations are applied explicitly (npm run migrate; npm run dev runs it first). The server refuses to start while
  migrations are pending.
- Pages are served with lang="pl" (the .NET app had "en"). The 404 and error pages are Polish ("Nie znaleziono
  strony", "Wystąpił błąd"); the .NET versions still had the template's English text. The error page shows the
  stack only in development.
- Every response sends X-Content-Type-Options: nosniff, X-Frame-Options: DENY, Referrer-Policy:
  strict-origin-when-cross-origin.
- GET /health returns {"status":"ok"} when the database answers (for deploy checks later).
- The drawer's Escape / link-click closing moved from inline attributes to public/js/layout.js; Escape now
  closes it from anywhere on the page (it used to need focus inside the drawer). "/stoly" also highlights
  "Zapisy na gry" in the drawer.

Phase 2 – accounts (decided 2026-11-10):
- Same pages, wording and rules as the .NET account pages, except these deliberate differences:
  - Lockout is ON: 5 wrong passwords in a row lock the account for 5 minutes (Identity's defaults). The .NET login
    passed lockoutOnFailure: false, so its lockout page was never reached.
  - Login with the right password but an unconfirmed e-mail says so ("Błąd: najpierw potwierdź adres e-mail – link
    jest w wiadomości od nas."); .NET showed the generic "nieprawidłowy login lub hasło". Only someone who knows the
    password sees it.
  - After registering, the confirmation page URL carries the user id instead of the e-mail address
    (/Account/RegisterConfirmation?userId=…), so addresses don't end up in server logs.
  - The Owner can't delete their own account on the personal-data page ("nobody can delete the Owner").
  - Profile menu: Profil, E-mail, Hasło, Dane osobowe (2FA, passkeys and external logins left out of v1). The
    registration page has no "Zarejestruj się przez inną usługę" column.
  - The personal-data download has the same keys as .NET, without the 2FA/authenticator entries.
  - Without EMAIL_HOST, Development also writes each unsent e-mail (with its link) to the log, so password reset and
    e-mail change can be tried locally. Never in production.
  - URLs are case-insensitive, as in ASP.NET Core (/account/login works).
- Sessions: stored in the database (sessions table, SHA-256 of the cookie's random id), 14 days, sliding;
  "Zapamiętaj mnie" = persistent cookie. Logout deletes the session; a password change logs out the user's other
  sessions, a password reset logs out all of them. Role changes apply on the next request.
- Cookies: HttpOnly, SameSite=Lax; in production also Secure with the __Host- prefix (__Host-session, __Host-csrf).
- CSRF: every POST needs the hidden _csrf field (signed token equal to the csrf cookie) and must not come from
  another site (Sec-Fetch-Site / Origin). Failure = 403 "Błąd: formularz wygasł albo został wysłany z innej strony…".
- Passwords: old ASP.NET Identity v3 hashes verify and are replaced by scrypt (N=2^14, r=8, p=5) on the next login.
  Password rules as Identity: production needs 6+ characters with a digit, lower- and upper-case letter and a
  special character; development only the length. Forms: 6–100 characters.
- E-mail links (confirm, change e-mail, reset password) use one-time random tokens valid 24 h, stored hashed.
- Roles are one column: owner / admin / user. The Owner comes from ADMIN_USER_NAME / ADMIN_EMAIL / ADMIN_PASSWORD.
- New settings: PUBLIC_URL (links in e-mails), APP_SECRET (required in production), ADMIN_*, EMAIL_* (see
  node-app/.env.example). Packages added: @fastify/cookie, @fastify/formbody, nodemailer, dev @types/nodemailer.
- Deleting an account (decided 2026-11-10): the user's seats and the tables they own STAY on the board. Only the
  link to the deleted account is cleared (user id set to null in the database), so the seat keeps showing the
  player's name and an owned table becomes a table without an owner (PlayTable already handles those).
  Built in phase 3 with the board tables.
- Admin "normal user mode" (decided 2026-11-10): stays, ported unchanged (admins switch it on to see the app as a
  regular user; the Admin/Owner roles are ignored app-wide until switched off). Built in phase 4 with the admin pages.

Phase 3 – board (decided 2026-11-10):
- Same board, rules and wording as Tables.razor (admin dock/toolbox, normal user mode and the sheet import come in phase 4).
- NEW: live updates. After every change the server sends all open pages a small notice (table id + version, no user
  data); each page re-fetches the changed row(s) with its own rights. Catch-up after a disconnect or server restart
  by version/boot id; reconnect with growing delays up to 30 s; a small "Łączenie…" notice after 3 s offline.
  WebSocket connections from other sites are refused (Origin check).
- Actions are fetch() POSTs (JSON, or multipart for a new table with a cover) with the CSRF token in a header;
  answers are JSON { ok, message | error } shown as the same dismissible alerts as in .NET.
- The meeting hour is stored as "HH:MM" only. Covers are served from /covers/<game id> (cacheable), not embedded.
- Uploaded covers are checked by content (magic bytes), max 2 MB enforced while receiving.
- The seat count of a hand-added game is still drawn at random (1–6) and re-checked on the server; a BGG game always
  uses BGG's count. New BGG_TOKEN setting (without it, lookups use the catalog and hand-added games only).
- Deleted accounts: their seats keep the name, their tables lose the owner (owner/user ids set to null).
- Packages added: fast-xml-parser, @fastify/websocket, @fastify/multipart; dev @types/ws, @playwright/test
  (+ Chromium for Playwright, downloaded to the PC only). npm run test:e2e runs the browser test.

Data (decided 2026-11-10):
- New clean schema (snake_case) plus a one-time, tested migration script (scripts/import-dotnet-db.ts) from the
  .NET app.db, run on a local copy in phase 4 and at cutover in phase 5.
- Existing ids are kept (user ids, table and game ids), so action-log entries and feedback files still match.
- Covers stay as BLOBs in the database. The BGG weight is kept as text, shown exactly as BGG gives it.
